# Structure: Neon Cube Arena

## Runtime layers

| Layer | Ownership | Responsibility |
|---|---|---|
| Next.js page shell | `src/pages/index.tsx` and lightweight React components | Customization flow, loading/error states, canvas host, and metadata. |
| Socket lifecycle | `src/components/SocketContext.tsx` | Initialize the API route, create one Socket.IO client, expose connection state and cleanup. |
| Game session | `src/game/GameSession.ts` | Own the client-side snapshot store, input state, interpolation targets, camera values, and render loop-facing data. |
| Canvas renderer | `src/game/CanvasRenderer.ts` | Draw the visible arena, cached assets, players, coins, background, and camera-follow effects. No React state updates inside the frame loop. |
| Input manager | `src/game/InputManager.ts` and mobile control adapters | Normalize keyboard, touch, and pointer actions into semantic control state. Emit changes only when values change and release stuck keys on blur. |
| HUD | `src/components/Leaderboard.tsx`, `Controls.tsx`, and small status components | React presentation updated from throttled snapshot events instead of polling mutable refs. |
| Authoritative server | `src/pages/api/socket.ts` plus map utilities | Own player physics, collision grid, coin lifecycle, round transitions, and network snapshot cadence. |
| Deployment health | `src/pages/api/health.ts` | Return a fast JSON health response with process uptime and server status. |

## Client data flow

```text
Socket.IO snapshots -> GameSession snapshot store -> CanvasRenderer at requestAnimationFrame rate
                                       \-> throttled HUD snapshot event -> React HUD
Keyboard/touch actions -> InputManager -> controls diff/heartbeat -> Socket.IO server
```

The canvas loop is intentionally independent from React rendering. React receives only coarse-grained HUD state, while the canvas reads stable session references and interpolates remote players between server snapshots. The local player uses the newest authoritative position as its anchor and renders immediately after input, avoiding an unnecessary UI state round-trip.

## Server data flow

```text
Socket.IO connection -> player registry + controls registry
Fixed simulation step -> input application -> collision-grid checks -> coin pickup -> round rules
Network snapshot cadence -> players/coins broadcast
Map reset -> collision-grid rebuild -> targeted map/block messages
```

The collision grid is derived once per map. Its solid tile list and row/column occupancy map are reused during every horizontal and vertical collision check. The tick loop does not allocate a new collidable array for each player or frame.

## Rendering contract

The canvas has one CSS size and a capped device-pixel backing store. The renderer clears only the visible frame, draws background layers and stars in screen space, converts world coordinates through a camera transform, and loops over the map only within the visible row/column bounds. Platform, coin, and player images are loaded once and reused. If an optional image fails, the renderer draws a procedural fallback rather than stopping the game.

## UI contract

The customization screen is a first-class state. Loading includes asset progress, socket connection state, and a recoverable error message. The active HUD contains a compact leaderboard, a match-status pill, a local player status panel, and desktop/mobile control hints. The obsolete dashboard placeholder is removed so all visible UI supports gameplay.

## Asset hints

Generated assets are optimized to small runtime dimensions and used as cached images. The platform asset is tiled at `TILE_SIZE`; the coin and player sprites are drawn at their gameplay sizes. Glows, stars, score bars, and panel borders are generated by the canvas/CSS because they are geometric and benefit from deterministic rendering.
